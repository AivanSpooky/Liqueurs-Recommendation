# Теория подходов ЛР3–ЛР4 (и РК1)

Подробный разбор всех принятых и отвергнутых решений: от выбора типа
рекомендательной системы до формул ранжирования, политик учёта дизлайков,
параметрического поиска и объединённой системы.

---

## 1. База: контентная фильтрация и релевантность

### 1.1. Почему контентная, а не коллаборативная

Рекомендательные системы делятся на два больших класса:

- **Коллаборативная фильтрация (CF)** — «пользователи, похожие на тебя, любили
  вот это». Требует матрицы оценок многих пользователей. В нашей задаче
  пользователь один, данных о других нет — CF неприменима физически.
- **Контентная (content-based)** — «тебе понравится то, что похоже на то, что
  ты уже любишь». Релевантность объекта считается по сходству его признаков
  с признаками лайкнутых объектов. Именно то, что у нас есть: гетерогенный
  каталог + обобщающая мера близости `sim(x, y) ∈ [0, 1]` из ЛР2.

Классические проблемы РС и как их решает контентный подход:

| Проблема | Суть | У нас |
|---|---|---|
| Холодный старт объектов | Новый объект без оценок CF не рекомендует | Нет: близость нового ликёра считается по признакам сразу |
| Холодный старт пользователя | Новый пользователь без истории | Достаточно одного лайка/затравки — это PCv1 |
| «Белая ворона» | Пользователь с редким вкусом — нет похожих пользователей | Нет: рекомендации строятся только по его профилю |
| Устаревшие предпочтения | Вкус меняется со временем | Учёт времени лайков (подход Б) + сброс профиля |
| Объяснимость | «Почему мне это советуют?» | Бесплатно: аддитивная мера раскладывается на вклады признаков |

Расплата — узкая специализация: система советует только похожее на уже
оценённое. Частично компенсируется учётом нескольких групп интересов (PCv2).

### 1.2. Как из близости получается список

Каждому кандидату `x` (объект каталога, ещё не оценённый пользователем)
ставится числовая оценка релевантности `r(x)`. Ранжированный список —
кортеж кандидатов по убыванию `r(x)`; при равенстве — по id, чтобы выдача
была детерминированной. Пользователю показывают первые `N`.

Все версии отличаются только тем, **как считается `r(x)`** — мера близости
одна и та же. Попарные близости предвычислены в матрицу 30×30: каталог
мал, пересчёт не нужен, доступ O(1).

### 1.3. Три версии системы

- **PCv1**: вход — один объект-затравка `s`; выход — top-N по `sim(x, s)`.
  Режим «хочу что-то похожее на вот это».
- **PCv2**: вход — набор лайков; нужен способ свести несколько близостей
  в одну оценку (раздел 2).
- **PCv3**: вход — лайки и дизлайки; добавляется коррекция оценки
  дизлайками (раздел 3).

## 2. PCv2: шесть способов учесть несколько лайков

Пусть `L = (l₁, …, l_m)` — лайки в порядке установки,
`s_i(x) = sim(x, l_i)`. Задача: из `m` близостей получить `r(x)`.

### А. Среднее арифметическое

`r(x) = (1/m)·Σ s_i(x)`

Просто и работает, если лайки — один интерес (среднее ≈ близость к «центру»
кластера). **Дефект «середины»**: при двух далёких друг от друга лайках
среднее поднимает объекты, лежащие между ними и не похожие ни на один.
Пример: лайки Amaro Averna (травяной) + Baileys (сливочный) → в top-5
лезет Ponche Crema, а Grand Marnier получает среднюю близость ~0.4 к обоим,
хотя не похож ни на один по-настоящему. Всё зависит от домена: в плотном
датасете «середина» — нормальный объект, в разреженном — фантом.

### Б. Учёт времени лайков

Взвешенное среднее, вес лайка `w_i = γ^(m−i)`, `γ = 0.7`:
последний лайк весит 1, предпоследний 0.7, и т.д.

Идея — вкус дрейфует, свежие предпочтения важнее; это одновременно ответ
на проблему устаревших предпочтений. Но дефект «середины» из А никуда не
делся — меняются только веса.

### В. Взвешенная сумма (баланс групп)

Веса задаёт не время, а структура профиля: `w_i = 1/|G(l_i)|`, где
`G(l_i)` — группа интересов лайка (как в подходе Г). Группа из пяти лайков
вносит в сумму столько же, сколько группа из одного — «сиротский» интерес
не тонет. Дефект «середины» формально остаётся, но смягчён.

### Максимум по лайкам

`r(x) = max_i s_i(x)` — близость к ближайшему лайку.

Никакой «середины»: каждый элемент выдачи реально похож на какой-то лайк
(лучший support из всех подходов). Дефект другой — монополия: самая
многочисленная/яркая группа интересов может занять всю выдачу, второй
интерес вообще не покажется.

### Г′. Сшивание списков по каждому лайку

Для каждого лайка строится свой список по убыванию `s_i(x)`, затем списки
сшиваются round-robin: первый объект от лайка 1, первый от лайка 2, …,
второй от лайка 1, … Дубликаты устраняются по первому вхождению.

Гарантия обслуживания каждого интереса: каждый лайк получает свою «очередь».
Дефект: три лайка одного интереса (три амаро) — это три очереди одного и
того же, интерес занимает лишние места.

### Г. Группы лайков + сшивание (выбран)

1. Лайки разбиваются на **группы интересов**: граф лайков, ребро между
   лайками, если `sim ≥ θ`; группы — компоненты связности (single linkage).
   Три амаро + Baileys → две группы, а не четыре списка.
2. Внутри группы `g`: `r_g(x) = (1/|g|)·Σ_{l∈g} sim(x, l)` — среднее здесь
   безопасно, потому что группа связная и «середина» между похожими
   объектами сама похожа на них.
3. Списки групп сшиваются round-robin: каждая группа получает очередь,
   размер группы не даёт ей захватить выдачу. Группы упорядочены по
   убыванию размера.

**Выбор θ = 0.65.** Порог должен склеивать лайки одного интереса и не
склеивать разные. Эмпирическая граница видна прямо в данных: пары из разных
ветвей L1 таксономии не превышают sim = 0.647, а медиана пар с общим L2
равна 0.667 — то есть 0.65 лежит ровно в разрыве. Перебор θ это
подтверждает: при меньших значениях разные интересы склеиваются и
coverage падает до ~0.83.

### Метрики качества

Выбор между подходами проверялся на смоделированных профилях: пользователь
с `k` интересами лайкает все объекты `k` групп L2 таксономии, кроме
последнего в каждой; отложенные объекты надо вернуть в top-5
(12/66/220 сценариев при k = 1/2/3).

- **recall(N)** — доля отложенных объектов в первых `N` позициях;
- **coverage(N)** — доля групп интересов, которым «служит» хотя бы один
  элемент выдачи (ближайший к нему лайк лежит в этой группе); метрика
  разнообразия выдачи по интересам;
- **support(N)** — средняя близость элемента выдачи к ближайшему лайку;
  низкое значение = рекомендации «не похожие ни на что».

### Итог сравнения (k = 3)

| Подход | recall(5) | coverage(5) | support(5) |
|---|---|---|---|
| А. среднее | 0.649 | 0.742 | 0.677 |
| Б. время | 0.733 | 0.808 | 0.681 |
| В. баланс групп | 0.747 | 0.836 | 0.691 |
| Максимум | 0.782 | 0.886 | **0.707** |
| Г′. по каждому лайку | 0.796 | 0.983 | 0.690 |
| **Г. группы + сшивание** | **0.797** | **1.000** | 0.693 |

При одном интересе все подходы одинаковы (recall 0.917, coverage 1) —
различия проявляются только при нескольких интересах. Г выбран как
единственный, который при k = 3 обслуживает все интересы без потери
recall; по умолчанию используется он, остальные доступны в интерфейсе.

## 3. PCv3: четыре политики учёта дизлайков

### 3.1. Почему дизлайк — это не «минус лайк»

Ключевой пример из лекции (домен музыки): пользователь любит весь жанр и
почти весь материал исполнителя, кроме **одной** композиции. Если
штрафовать всё, что похоже на эту композицию, система «испортит» весь
любимый жанр. Правильная семантика: **дизлайк уточняет интерес, а не
отменяет его**.

Анкетирование о причинах неприязни отвергнуто: длинная анкета утомляет,
пользователь уйдёт. Причину надо выводить из соотношения лайков и
дизлайков самим.

Обозначения: `dis(x) = max_{d∈D} sim(x, d)` — близость к ближайшему
дизлайку; `sup(x) = max_{l∈L} sim(x, l)` — близость к ближайшему лайку.
Политика — это функция-корректор оценки кандидата: либо возвращает
скорректированный `r'(x)`, либо исключает объект из выдачи.

### Политика 1. Только исключить дизлайки

Из выдачи убираются сами дизлайкнутые объекты, остальные оценки не меняются.
Базовый вариант: безопасен (не портит жанр), но почти не реагирует на
дизлайк — похожие на него объекты спокойно рекомендуются.

### Политика 2. Исключить похожие на дизлайки

Убрать `x`, если `dis(x) ≥ τ` (τ = 0.7).

Простая и объяснимая, но жёсткая: у дизлайка из любимого жанра «ближние
родственники» имеют sim ≥ 0.7, и весь жанр выпадает из выдачи. Подтверждает
лекционный пример дословно: recall внутри любимого жанра падает до 0.45.

### Политика 3. Штраф за близость к дизлайку (вычитание, аналог Роккио)

`r'(x) = r(x) − β·dis(x)`

Формула обратной связи Роккио из информационного поиска: двигаемся «к
релевантному, от нерелевантного». При β = 1 эффект тот же, что у политики 2,
только мягче: любимый жанр не исключается, но опускается настолько, что из
top-5 пропадает (recall 0.37, выдача — объекты с оценками 0.07–0.11).
При малом β = 0.25 жанр сохраняется, но утечка нелюбимого стиля хуже, чем у
политики 4.

### Политика 4. Контрастный штраф (выбрана)

`r'(x) = r(x) − β·max(0, dis(x) − sup(x))`

Штрафуется только то, что **ближе к дизлайку, чем к любому лайку**:

- объект любимого жанра близок и к дизлайку, и к лайкам того же жанра →
  `dis ≈ sup` → штраф ≈ 0 → жанр сохраняется;
- объект, похожий именно на нелюбимый образец (ближе к нему, чем к любому
  лайку) → `dis > sup` → штраф положительный → опускается.

Это формализация интуиции «дизлайк уточняет, а не отменяет интерес»:
дизлайк внутри любимого жанра вырезает узкую нишу вокруг себя, не трогая
жанр целиком; дизлайк чужого жанра давит именно чужое.

**Отдельный режим — только дизлайки** (лайков нет):
`r(x) = 1 − dis(x)` — рекомендуется то, что дальше всего от нелюбимого.

### Протокол проверки и итог

Два требования проверяются двумя сценариями:

- *дизлайк внутри любимого жанра* (38 сценариев) — жанр должен сохраниться;
- *дизлайк чужого жанра* (132 сценария) — остальные объекты чужого жанра
  не должны рекомендоваться; мера **leakage(N)** — доля таких «протекших»
  объектов в выдаче.

Итоговая таблица (стратегия лайков Г, N = 5):

| Политика | recall, свой жанр | recall, чужой жанр | leakage |
|---|---|---|---|
| 1. только исключить | **0.974** | 0.917 | 0.049 |
| 2. порог τ = 0.7 | 0.447 | 0.924 | 0.029 |
| 3. вычитание β = 1 | 0.368 | 0.902 | 0.002 |
| 3. вычитание β = 0.25 | 0.921 | 0.939 | 0.023 |
| **4. контрастный β = 1** | **0.921** | **0.932** | **0.017** |

Политика 1 сохраняет жанр лучше всех, но пропускает втрое больше нелюбимого.
Выбран контрастный штраф с β = 1: компромисс «жанр почти целиком сохранён +
утечка минимальна из щадящих». Пример: лайк Baileys, дизлайк Advocaat →
яичный Ponche Crema (sim к Advocaat 0.727 против 0.504 к Baileys) падает
со 2-го на 5-е место, а Amarula рядом с Baileys не трогается.

## 4. Объяснение рекомендаций

Каждая рекомендация объясняется бесплатно, потому что итоговая мера ЛР2
аддитивна:

- **anchor** — ближайший лайк («похож на Baileys») и номер группы интересов;
- **вклады признаков** — слагаемые `ω_k·sim_k` (вкус +35 %, числовые +30 % …)
  показываются по запросу;
- **blame** — если сработал штраф, показываются его размер и дизлайк,
  на который похож объект.

## 5. ЛР4: параметрический поиск

### 5.1. Семантика запроса

Поиск отвечает на вопрос «дай мне то, что я сам описал», а не «угадай, что
мне понравится». Семантика — как у фильтров интернет-магазина:

- разные фильтры объединяются **конъюнкцией** (травяной И ≤ 30 % И Италия);
- значения внутри одного фильтра — **дизъюнкцией** (Франция ИЛИ Италия);
- незаданный фильтр не ограничивает; пустой запрос = весь каталог.

Десять фильтров покрывают все типы признаков датасета: строка (название/
производитель), дерево вкуса L1–L3, диапазоны крепости/сахара/объёма,
флажки класса сладости, трёхзначные флаги горечи и выдержки в дереве,
мультивыборы страны и производителя.

### 5.2. Нетривиальные решения по фильтрам

- **Вкус — узлами, а не только листьями.** Выбор «Травяные» включает всё
  поддерево: пользователь может быть точным («амаро») или общим
  («что-нибудь травяное»), не отмечая листья вручную.
- **Текст без регистра и диакритики** («KAHLUA» → «Kahlúa», «creme» →
  «Crème») + нечёткое совпадение `difflib.SequenceMatcher ≥ 0.7` при
  опечатках («kalua» → Kahlúa с весом 0.8). Порог 0.7 отсекает случайные
  совпадения: без него «kalua» матчился бы с девятью посторонними.
- **Сладость двумя способами**: точный диапазон г/л и термы лингвистической
  переменной из ЛР1 — покупатель редко знает сахар в граммах.
- **Проверка ввода** — на сервере, все ошибки собираются разом: синтаксис
  чисел (запятая и точка допустимы, `10x`/`nan`/`inf` отклоняются),
  физические границы (крепость 0–100 %, «от» ≤ «до»), значения только из
  справочников. Границы за пределами датасета, но физические — не ошибка,
  а повод для fallback.

### 5.3. Пустая выдача: три подхода

Требование: вместо пустого экрана — «не найдено точного соответствия,
однако, возможно, Вам понравится».

1. **Рекомендации по профилю** — отклонены как основной механизм: лайков
   может не быть вовсе, и рекомендации игнорируют сам запрос.
2. **Ослабление фильтров (query relaxation).** Жадный алгоритм
   `RelaxationAdvisor`: на каждом шаге каждый фильтр ослабляется на шаг
   (снять / расширить на 10 % размаха / подняться к родителю дерева /
   добавить соседние термы) и выбирается вариант, дающий точные совпадения
   или максимально повышающий лучшую степень соответствия; при равенстве —
   минимальная «цена» (вес фильтра, для расширения — половина). Объяснимо
   («ослабьте крепость до 19 %»), но ослабленное ограничение снимается
   целиком для всех — выдача может уйти в сторону.
3. **Функция полезности U(x)** — мягкие ограничения:

   `U(x) = Σ_f w_f·deg_f(x) / Σ_f w_f`

   где `deg_f(x)` — степень выполнения фильтра `f`: 1 внутри диапазона,
   линейно до 0 при выходе за границу на 25 % размаха; для вкуса — доля
   общего пути с ближайшим выбранным узлом; для термов сладости —
   `1 − |ord(x) − ord(терм)|/3`. Веса `w_f` отражают важность (название и
   вкус = 3, диапазоны = 2, флаги = 1–1.5, объём = 0.5). Нарушение на 1 п.п.
   крепости почти не штрафуется, на 20 п.п. — полностью.

**Проверка** — протокол «восстановления задуманного объекта»: для каждого
ликёра строится запрос по его признакам, затем два ограничения портятся
(крепость ±3–8 п.п., сахар ±20–60 г/л, другая страна, инвертированная
горечь) так, что точных совпадений нет — 179 сценариев. Метрика Hit(k) —
доля сценариев, где задуманный объект попал в top-k:

- ослабление: Hit(1) = 0.60, Hit(5) = 0.70 — в 30 % сценариев жадный шаг
  снимает не то ограничение;
- **U(x): Hit(1) = 0.64, Hit(5) = 1.00** — задуманный объект ни разу не
  выпал из первой пятёрки.

**Комбинированное решение:** выдача ранжируется U(x), а результат
RelaxationAdvisor показывается подсказкой («снимите горечь и расширьте
крепость до 19 % — будет 2 точных совпадения»). У каждого объекта
указываются невыполненные фильтры и степень их выполнения.

## 6. РК1: объединённая система

### 6.1. Цикл работы

`поиск → лайки/дизлайки на карточках → рекомендации → уточнение фильтрами → …`

- **Профиль в сессии**: лайк/дизлайк доступен на любой карточке любой
  выдачи и не теряется между шагами.
- **Автовыбор версии**: один лайк → v1, несколько лайков → v2, есть
  дизлайки → v3. Можно рекомендовать по всему каталогу или «среди текущей
  выдачи».
- **Уточнение** фильтрует результат текущего шага (поиска или
  рекомендаций), сохраняя порядок и объяснения.
- **История шагов**: каждый шаг сохраняется, клик по записи восстанавливает
  и выдачу, и форму фильтров; «Начать заново» чистит историю, оставляя
  лайки; «Сбросить всё» — полный сброс.
- Рекомендательное ядро **не копируется**: `bootstrap.py` подключает пакет
  `recsys` из `3-likesdislikes` как есть.

### 6.2. Фильтрация рекомендаций функцией полезности

У объекта две оценки: рекомендательная `r(x)` и соответствие фильтрам
`U(x)`. Итоговая полезность:

`S(x) = U(x)·((1 − λ) + λ·r(x))`, `λ = 0.5`

- есть точные совпадения (U = 1) → порядок рекомендателя сохраняется,
  включая чередование групп интересов из PCv2;
- точных нет → ранжирование по S(x);
- **почему произведение, а не сумма**: сильная рекомендация не должна
  компенсировать полное нарушение фильтров (U = 0 ⇒ S = 0); λ = 0.5 даёт
  рекомендации право менять оценку максимум вдвое — явно заданные фильтры
  главнее.
